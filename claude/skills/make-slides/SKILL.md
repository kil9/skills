슬라이드를 넘기며 혼자 읽어도 이해되는 덱을 만든다. 디자인은 정해 두었으니 **내용과 장 구성에 힘을 쓴다.**
아래 §3 규칙이 이 스킬의 본체다 — 일반적인 "좋은 발표" 조언으로 바꿔 읽지 말고 문자 그대로 지킨다.

## 1. 착수: 묻고 정한다

새 덱이면 만들기 전에 아래를 정한다. 사용자가 이미 말한 것은 묻지 않는다. 정한 것은 프로젝트의 `OUTLINE.md`
첫머리에 적어 둔다 — 뒤에 덱을 나눠 쓰는 서브에이전트도 이 결정을 받아야 한다.

| 정할 것 | 기본값(사용자가 따로 말하지 않으면) |
|---|---|
| 대상 | 기본 엔지니어링은 알지만 이 주제는 처음인 현업 엔지니어. 친절하게 |
| 형식 | 강의형(`LECTURE=True`): 덱마다 표지(목표) → 본문 → 요약 → 확인 문제 → 정답. 발표형이면 요약까지 |
| 분량 | 덱 수와 총 장수 범위(`TOTAL`). 덱 하나 15-25장 |
| 예제 | 독자가 실제로 다루는 시스템·숫자. 수식은 산수(곱·나눗셈·합) 수준 |
| 사례 | 실명·실제 번호·실측값 그대로(출처 줄 필수). 지어낸 사례 금지 |
| 실습 | 없음(읽기 자료) |
| 보는 법 | 로컬 미리보기로 사용자 혼자 본다. 게시는 사용자가 따로 요청할 때 별도 스킬로 |

## 2. 만드는 순서

스크립트는 `~/.claude/skills/make-slides/scripts/` 에 있다(아래 `$S`). 부품 API 는 `references/api.md`.

1. **골격.** `template/` 을 새 프로젝트 디렉터리로 복사하고 `course.py`(제목·덱 목록·`TOTAL`)를 채운다.
   `OUTLINE.md` 에 덱마다 "마치면 할 수 있는 것" 2-4개와 장 제목 목록을 쓴다. 첫 덱 하나를 표·그림·용어표·요약·
   문제 레이아웃 견본으로 먼저 끝까지 만들어 사용자에게 보인다.
2. **본문.** 덱별로 `content/dNN.py` 의 `build(D)` 를 쓴다. 덱이 많으면 두 덱씩 서브에이전트에 나눠 맡기되,
   §1 결정·§3 규칙·`OUTLINE.md`·용어집(앞 덱에서 이미 푼 용어)을 프롬프트에 넘긴다.
3. **빌드·검사·캡처.** 고칠 때마다 이 셋을 돈다.
   ```bash
   python3 $S/build.py <dir> [N...]            # out/dNN.html, out/index.html (--outline 은 OUTLINE.md 빌드 목록 갱신)
   python3 $S/check.py <dir> [N...] --render    # 규칙 검사 + 넘침·제목 겹침·SVG 글자 잘림
   python3 $S/shot.py <dir> N [장...]           # ~/.cache/make-slides/shots/<dir이름>/dNN-MM.png
   ```
   `check.py` 가 PASS 여도 **캡처를 눈으로 본다.** 기계가 못 잡는 것: 그림 안 글자끼리 겹침, 한쪽으로 쏠린 빈 공간,
   제목과 그림이 말하는 것이 다름.
4. **통합 검수**(덱이 여럿이면 한 번): 덱 사이 같은 사실·숫자가 같은지, 용어가 처음 나온 곳에서 풀렸고 이름이
   통일됐는지, 제목 어미가 '-다' 로 통일됐는지, 지운 장을 가리키는 참조("강의 3 의 12장")가 남지 않았는지.
5. **한국어 윤문**: 전 장을 한 번 훑어 번역투·비유 표현·호응을 고친다(`/korean-polish` 가 있으면 그것으로).
6. **그림 보강 패스**: 전 장을 다시 훑어 표나 문장만으로 **흐름·비율·크기 비교·시간 순서**를 설명하는 장을 골라
   정적 SVG 를 넣거나 표를 그림으로 바꾼다. 표·목록이 본체인 장(대응표·설정값·결정 목록)과 숫자 근거가 없는 장은 둔다.
7. **보여 주기**: 로컬 정적 서버(`/web-show` 가 있으면 그것)로 `out/` 을 띄워 URL 을 준다. 커밋은 소스
   (`course.py`·`content/`·`OUTLINE.md`)만 경로로 add 하고 `out/` 은 gitignore 한다.

이미 있는 덱을 고칠 때(사용자가 장을 보며 질문·지적할 때): 그 장의 원본 `content/dNN.py` 를 고치고 3번을 그 덱만
돌린다. 질문 자체가 신호다 — "X 가 뭐야?" 는 그 장에 X 풀이가 없다는 뜻이니 답한 뒤 **그 장에 한 줄을 넣을지**
제안한다(§3-3). 같은 종류의 지적이 나오면 전 덱에서 같은 문제를 찾아 함께 고친다.

## 3. 장표 규칙

### 3-1. 주인공은 표·그림, 문장은 읽는 법

- 모든 장에 표(`table`·`terms`)나 정적 SVG(`svg`)가 하나 이상 있다(✓ check).
- 문장(`say`)은 **장당 4줄, 한 줄 110자까지**(✓). 문장은 표·그림을 **어떻게 읽나** — 어디를 보고 무엇을 읽어
  내면 되는지 — 만 말한다. 표에 있는 값을 문장에서 되풀이하지 않는다.
- **설명 문장 대신 배치·범례·축 이름.** 문장형 범례는 기호와 짧은 라벨로 바꾼다.
  - 나쁨: `say("막대 색은 상태를, 높이는 사용률을, 빨간 테두리는 과열을 뜻합니다.")`
  - 좋음: 그림 안에 `■ 정상 ■ 대기 □ 과열` 범례 한 줄, 축 이름 "사용률(%)". 문장은 결론 한 줄만.
- **정적 그림이 기본이다.** 슬라이더·토글·재생 버튼은 조작해서 독자가 **새로 알게 되는 것**이 있을 때만 — 경우가
  몇 가지뿐이면(상태 3개, 경로 6개) 전부 펼친 한 장이 빠르다. '인터랙티브하게' 라는 요청도 이 기준으로 걸러
  필요 없는 것은 정적으로 두고 이유를 보고한다.

### 3-2. 한 장은 한 주장, 제목이 그 주장이다

- 제목(`h2`)은 그 장의 **결론 한 문장**, '-다' 로 끝낸다.
  - 나쁨: "KV cache" / "인덱스 구조"
  - 좋음: "KV cache 는 요청이 길수록 GPU 메모리를 더 먹는다" / "B-tree 는 높이만큼만 내려가 행을 찾는다"
- **제목과 관계없는 숫자는 뺀다.** 원리를 설명하는 장에 실측 막대를 곁들이면 시선이 숫자로 가고 원리가 묻힌다.
  실측은 그 실측이 주장인 장에 따로 둔다.
- **제목과 표·그림이 같은 말을 하는지 대조한다.** "평균이 아니라 최대로 본다" 는 제목 아래 첫 행이 평균 쿼리면
  독자는 어느 쪽을 믿을지 모른다.
- '왜 필요한가' 를 '어떻게 하나' 보다 먼저: 기술을 소개하는 장 앞에 그것이 없을 때 생기는 문제를 보이는 장을 둔다.

### 3-3. 덱만 보고 혼자 이해된다

독자는 발표자 없이 넘겨 본다. 질문이 나올 만한 곳을 그 장 안에서 막는다.

- **새 용어는 처음 나온 장에서 한 줄로 푼다.** `terms()` 표(용어 · 뜻 · 익숙한 것에 빗대면)나
  `say("<b>용어</b>: 한 줄 뜻")`. 빗댄 말은 셋째 열에만, 정의는 '뜻' 열이 기준. 앞 덱에서 푼 용어는 용어집에
  올리고 뒤 덱은 다시 풀지 않는다.
- **숫자 상수는 어디서 왔는지 같은 장에.** "0.85 × 80GB" 가 나오면 0.85 가 무슨 설정의 기본값인지 한 줄.
- **번호·기호는 같은 장에서 범례로 푼다.** 그림에 ①-⑥ 을 달았으면 그 장에 ①-⑥ 이 뭔지 있어야 한다("뒤에 나온다"
  는 안 된다).
- **열 이름·셀 문구는 무엇을 무엇으로 하는지 드러나게.**
  - 나쁨: 행 "계산 기준" / 셀 "H100 으로 계산" (H100 의 무엇으로 무엇을?)
  - 좋음: 행 "이 강좌의 속도 예제" / 셀 "이 열의 대역폭으로 셈"
- 열 이름만으로 뜻이 안 서면(예: "버전" 열이 무엇의 버전이고 누가 정했나) 표 아래 한 줄로 푼다.
- **실측표는 조건이 제목·출처에서 읽혀야 한다.** 부하를 3배로 몰아 잰 시험값을 조건 없이 두면 독자는 "지금 상태가
  이렇게 나쁜가" 로 읽는다. 극단 조건 값이면 현재 실제 값과 나란히 두거나 실제 값으로 바꾼다.
- **'우리' 를 쓰지 않는다** — 운영 조직인지 분석한 본인인지 섞인다. 주체를 이름으로("운영팀 설정", "이 분석의 쿼리").

### 3-4. 말: 실무 용어, 평범한 문장

- **풀어 쓴 낯선 말보다 실무에서 늘 쓰는 짧은 용어.** '위쪽 한계' → 상한, '아래쪽 한계' → 하한. 한 번 지적되면
  전 덱에서 바꾸고 이후에도 쓰지 않는다.
- 문장은 '-습니다' 체, 표 셀은 명사형·짧은 구, 제목은 '-다'.
- **가운뎃점(·)은 표 셀·라벨에서만.** 문장 속 나열은 쉼표로(✓ WARN).
  - 나쁨: "커넥션 풀 · 버퍼 풀 · 쿼리 처리기를 갖춘 DB 서버"
  - 좋음: "커넥션 풀, 버퍼 풀, 쿼리 처리기를 갖춘 DB 서버"
- 무형의 것(기능·조건·시점·범위)을 장소·사물에 빗대 가리키지 않는다('~하는 자리', '손잡이' 류 ✓ WARN).
  관계에 이름을 붙인다(줄·단계·시점·명령·플래그).
- em-dash(—) 금지(✓), 범위는 `-`(`3-5개`), `~` 금지(✓). 메모리는 한 단위(GB 면 GB)로만 센다.
- 숫자는 원천(문서·측정 결과·설정 파일)에서 가져온다. 기억으로 쓰지 않고, 모르는 값은 지어내지 말고 뺀다.
  확인하지 못한 것은 출처 줄에 "(미확인)" 으로 적는다. 실측값에는 `src()` 를 반드시 단다.
- **덱은 늘 처음 쓰는 문서처럼.** 고칠 때 "이전 판에서 바뀐 것", "v2 대비" 를 쓰지 않는다. 그 장을 지금 결론으로
  다시 쓴다(✓ WARN).

### 3-5. 시각: 밀도, 장식 없음

- **밀도가 먼저다** — 쓸모 있는 정보로 채운다. 같은 값을 되풀이해 채우지 않고, 글자를 줄여 밀도를 내지도 않는다.
- **장식하지 않는다.** 아이콘·이모지 도배, 그라데이션, 그림자 금지.
- **카드·행·패널의 한쪽 가장자리에 색 띠(굵은 왼쪽 테두리 등)를 절대 붙이지 않는다.** 강조하겠다고 새 색 +
  칩(뱃지) + 색 테두리를 두르는 조합도 AI 생성물처럼 보인다. 구분은 **바탕 톤과 굵은 제목 글자**로 한다 —
  `aside()` 가 그렇게 그린다.
- 본문과 출처가 다른 정보(외부 발표 내용, 현재 운영 현황, 계획)는 `aside()` 곁들임 패널로 분리한다. 패널 이름은
  내용을 말하고(예: "지금과 계획"), "확인하지 않은 값" 같은 면책 꼬리표를 머리줄에 달지 않는다 — 확인 여부는
  출처 줄에. 대신 맥락(지금 상태 · 계획 · 그 계획의 전제)을 한 줄씩 준다. 3줄까지(✓).
- 메타포 금지: 화면을 다른 사물처럼 꾸미지 않는다. 색이 뜻을 실으면 같은 뜻의 말 라벨은 뺀다.
- 위계는 의미에서: 강조(`hl` 행, `acc` 상자)는 장마다 하나 정도, 그 장의 주장에 해당하는 것에만.
- 색은 CSS 토큰(라이트·다크)과 SVG 클래스로만 준다. 인라인 색 지정 금지.

### 3-6. 레이아웃 함정

- **그림이 제목과 겹치면 그림을 줄인다**(막대 높이·항목 수·`maxh`). 본문이 넘치면 세로 가운데 정렬 때문에 위로
  밀려 제목을 덮는다 — `check.py --render` 가 "본문 넘침/제목과 겹침" 으로 잡는다.
- SVG 는 반드시 `viewBox`(✓), 글자가 viewBox 밖으로 나가면 잘린다(✓ --render).
- 화살촉 marker id 는 문서 전체에서 유일해야 한다. `svg()` 가 일련번호를 붙이니 marker 를 손으로 정의하지 않는다
  (같은 id 가 여럿이면 숨은 슬라이드의 marker 를 먼저 잡아 둘째 장부터 화살촉이 사라진다).
- 외부 리소스(CDN 스크립트·폰트·이미지 URL) 금지(✓). 덱은 파일 하나로 열린다.

## 4. 디자인 방향을 바꿔야 할 때

기본 CSS(`deck.py`)는 위 규칙에 맞춰 둔 것이라 손대지 않는 것이 기본이다. 사용자가 시각 방향을 바꾸자고 하면
아스키 스케치로 묻지 말고, **같은 장 두세 개를 후보 방향마다 HTML 로 그려 나란히 띄운 뒤** 고르게 한다. 고른
방향은 `deck.py` 의 CSS 토큰만 바꿔 반영하고 §3-5 를 그대로 지킨다.
