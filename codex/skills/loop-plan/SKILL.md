레거시 `PLAN*.md` 계획을 **스스로 진행할 수 있는 태스크가 남지 않을 때까지** 라운드 단위로 자율 드레인한다(backlog 백엔드는 `$loop-backlog`). 각 라운드: **fresh 재조회 → ready set → 실행 → 발견분 자동 추가**. 각 태스크는 구현 → 검증 → 커밋(`$start-backlog` 레거시 규칙)으로 완결한다. **한 번 읽고 비었다고 종료하지 않고**(§5), **인터랙티브 질문으로 멈추지 않는다**(§3).

## 0. 전제 · snapshot

매 라운드 `bash ~/.codex/skills/next-backlog/plan-context.sh --dump`를 **한 번만** 호출해 `## primary` / `## numbers` / `===== PLAN... =====` 원문만 읽고 glob·파일 읽기를 반복하지 않는다. exit 1이면 backlog가 있으면 `$loop-backlog`, 아니면 `$make-a-plan`을 안내한다. 상태 `[ ]` / `[→]` / `[x]` / `[!]`와 `T-N`·`M-N`·`I-N`의 비표준 표기는 원문 근거로 존중한다.

## 1. 라운드 · ready set

매 라운드 새 dump를 읽어 이전 내용은 재사용하지 않는다. 외부 세션·사용자의 편집도 다음 snapshot에 반영한다.

ready set = 지금 스스로 착수 가능한 태스크:

- `[→]` IN_PROGRESS(이어서 진행 — 최우선).
- `[ ]` TODO 중 의존(`의존:` 필드, 없는 구식 플랜은 본문의 선행 관계)이 모두 `[x]` 이고 **self-actionable**(진행에 사용자의 중대한 결정이 필수가 아님 — §3).
- `[!]` 는 제외하되, 막힘 사유가 해소된 게 확인되면 `[ ]` 로 되돌려 포함. `I-N`·`M-N` 은 제외.

## 2. 실행 (위임 우선 · 병렬은 독립성 기준)

ready set을 우선순위·의존 순으로 실행 packet으로 만들고 `$lunamax-threads`에 배분한다. 각 태스크는
`$start-backlog` 레거시 규칙대로 구현 → 검증 → 태스크 단위 커밋으로 완결한다. PLAN 상태 갱신은
병렬 worktree 충돌을 피하려고 Sol이 순차 통합 단계에서 맡는다.

위임과 병렬화를 분리해서 판단한다.

- 목표·비범위·cwd·소유 범위·완료 조건·검증법이 닫힌 packet이면 quota 우선 상황에서 크기가 작아도
  Luna max에 우선 위임한다. 사용자가 빠른 피드백을 요구하거나 latency가 우선인 태스크는 Luna max를
  강제하지 말고 Sol direct 또는 호출자가 정한 더 빠른 구성을 쓴다. 포장이 실행보다 명백히 큰 극소
  작업만 Sol이 직접 하고, 관련 극소 작업은 한 packet으로 묶는다.
- 독립 packet이 2개 이상이고 write 충돌이 없으며 `단독실행: 필요`가 아니면 크기와 무관하게 병렬
  실행한다. 작업량 문턱은 두지 않는다. Sol을 남겨 두고 나머지 가용 슬롯을 모두 쓴다.
- `단독실행: 필요`는 위임 금지가 아니라 동시 실행 금지다. 해당 태스크는 다른 packet 없이 단독
  실행한다.
- 생성물·lockfile·migration·공유 설정을 겹쳐 만지는 태스크는 같은 worker에 묶거나 직렬화한다.

writer는 태스크별 격리 worktree에서 코드 구현·검증·커밋까지 하고, Sol은 성공 브랜치를 순차 통합한
뒤 PLAN 상태와 진행 로그를 갱신한다. 상세 절차와 충돌 처리는
[`../references/parallel-worktree.md`](../references/parallel-worktree.md)를 따른다. worker packet에는
"발견한 선행·후속 작업을 RESULT로 보고"를 넣고, Sol이 통합 뒤 §4에 따라 PLAN에 추가한다.

## 3. 하이브리드 막힘 정책 (질문으로 멈추지 않는다)

- **사소한 결정**(네이밍·에러 처리·라이브러리 세부 등 되돌리기 쉬운 것): 스스로 합리적으로 정해 진행. 영향이 크면 PLAN 에 `### 디자인 결정: <제목>`(날짜·결정·이유·대안) 블록으로 기록해 커밋에 포함.
- **사용자 몫인 중대한 갈림길**(결과를 크게 바꾸거나 되돌리기 어려움): 추측으로 밀지 않는다. 상태를 `[!]` 로 바꾸고 상태 라인에 `결정 필요: <질문 한 줄>` 을 병기한 뒤 다음 태스크로. self-actionable 이 아니므로 종료를 막지 않는다.
- **재실행으로 풀릴 일시적 실패**(flaky·환경): `[!]` 아님 — `[ ]` 유지 + 진행 로그에 실패 요약 append, 다음 라운드 재시도. 같은 태스크가 반복 실패하면 그때 `[!]` 로 전이한다.

## 4. 발견분 자동 추가

기존 태스크 완료에 **실제로 필요한** 선행·후속 작업(누락된 마이그레이션, 선행 리팩터, 완료 조건을 막는 버그 등)을 발견하면 즉시 `T-N` 태스크로 추가해 다음 라운드가 집게 한다:

- 번호 = 대상 플랜들 전체에서 기존 `T-N` 최대값 + 1(전역 카운터, 재사용 금지). 적절한 마일스톤 아래 맨 밑에 `[ ]` 로.
- 표준 필드: `완료 조건:`·`의존:`(없으면 `없음`)·`범위 힌트:`(파악된 파일만)·`단독실행:`(병렬 비안전 시만 `필요 — <사유>`)·`접수:`(오늘). 본문 첫 줄에 `loop-plan 자동 추가: <발견 맥락>`.
- **scope creep 경계**: "있으면 좋은" 개선은 `T-N` 이 아니라 `## 아이디어 (보류)` 의 `I-N` 으로(ready set 밖).
- 자동 추가분의 완료 조건 자체가 사용자 결정을 요하면 만들되 §3 대로 `[!]` 로 둔다.

## 5. 종료 (연속 2회 빈 조회 필수)

ready set 이 비어도 **즉시 종료하지 않는다** — 외부 세션·사용자가 방금 태스크를 추가·편집했을 수 있다. 빈 라운드 뒤 §1 로 **한 번 더 다시 읽어** 그것도 비었을 때만 종료한다(연속 2회 빈 조회). 새 태스크가 생겼으면 라운드를 재개한다.

**수렴 안전장치**: 자동 추가(§4)가 새 태스크를 계속 만들어 미완료가 줄지 않으면(예: 3라운드 연속 완료 0 · 신규만 증가) 무한 루프로 보고 멈추고 남은 태스크를 사용자에게 알린다.

## 6. 마무리

PLAN 은 세션 리셋 후에도 재개 가능한 진실원본이다 — 라운드/커밋 경계에서 세션 리셋 후 이 스킬을 다시 호출해도 손실이 없다. 종료 시 보고: 완료(파일·ID·제목)·자동 추가·`[!]`(사유·질문 포함) 태스크, 기록한 설계 결정, 종료 근거. 완료(`[x]`) 태스크가 5개 이상이면 작업 ID·한 줄 요약만 남기도록 압축을 한 줄로 권고한다.
