# Sol Advisor

사용자가 `/sol-advisor` 또는 `$sol-advisor`를 직접 적었을 때만 Sol을 자문역으로 호출한다. 계획의
중요도나 난도만으로 이 스킬을 자동 호출하지 않는다.

## 1. 자문 대상과 모드 결정

자문 대상을 다음 순서로 정한다.

1. 호출과 같은 메시지에 있는 요청이나 초점을 사용한다.
2. 호출만 있으면 직전 대화의 가장 실질적인 요청·초안·계획을 사용한다.
3. 대상이 여전히 불명확하면 한 가지 짧은 질문으로 확정한다.

상황에 맞게 한 모드를 고른다.

- 검토·비평: 먼저 만든 답안·계획·diff의 허점과 대안을 검토한다. 기본 모드다. Sol은
  `VERDICT: accept | revise | rethink` 중 하나와 결정적 이유, 구체적 지적, 가장 큰 잔여 위험을 반환한다.
- 선조언: 아직 방향을 정하지 않았거나 큰 되돌림 비용이 예상될 때 먼저 관점을 받는다. 제안한 결정과
  대안을 주고, Sol은 `VERDICT: proceed | change | stop` 중 하나와 결정적 이유, 계획을 바꿀 한 가지 질문,
  가장 큰 위험을 반환한다.
- 병기: 정답이 하나가 아닌 판단에서 주 에이전트와 Sol 관점을 합치지 않고 나란히 제시한다.

## 2. 독립 자문 호출

`collaboration.spawn_agent`를 한 번 호출한다. 사용자가 여러 자문을 명시하지 않은 한 agent 하나만 쓴다.

- `agent_type`: `default`
- `model`: `gpt-5.6-sol`
- `reasoning_effort`: `high`
- `fork_turns`: `none`
- `task_name`: 작업을 나타내는 짧은 snake_case 이름

`fork_turns=none`이라 자문 agent는 대화를 상속하지 않는다. `message`에 다음을 자급자족하도록 넣는다.

- 사용자의 원래 목표와 선택한 자문 모드
- 검토할 답안·계획 전문, 또는 변경 파일과 전체 diff나 명시적인 base/head revision
- 보존할 인터페이스, 제약, 제외 범위
- 주 에이전트가 직접 확인한 검증 명령과 실제 결과
- 관련 파일의 절대 경로와 읽을 범위
- 이번 자문의 초점과 모드별 기대 출력

검증 결과가 아직 없으면 없다고 명시하며 만들어내지 않는다. 자문 agent에게 읽기 전용으로 행동하고,
관련 파일과 실제 변경분을 읽어 조언만 반환하도록 한다. 구현·파일 수정·외부 게시는 맡기지 않는다.
코드나 파일을 검토할 때는 호출 직전 관련 저장소와 산출물 상태를 기록하고 완료 뒤 다시 확인한다. 자문
agent가 이를 바꿨으면 판정을 폐기하고 변경 사실을 보고한다.

호출 뒤 `collaboration.wait_agent`로 완료를 기다리고 최종 응답을 회수한다. 실패하면 모델 식별자와 API
오류를 그대로 요약하고, 다른 모델로 조용히 대체하지 않는다.

## 3. 비판적 반영과 전달

자문을 정답으로 취급하지 않는다. 근거를 원 요청·코드·문서와 대조해 다음처럼 처리한다.

- 타당한 지적은 답안이나 계획에 반영한다.
- 근거가 약하거나 제약과 충돌하는 제안은 제외하고 이유를 남긴다.
- 병기 모드는 `주 에이전트 관점`과 `Sol 관점`을 분리해 보여준다.

자문 뒤 검토 대상이 실질적으로 바뀌면 이전 판정은 새 결과에 유효하지 않다. 최종 결과에 대한 Sol 판정이
필요하면 새 agent로 다시 검토하고, 그러지 않으면 이전 판정을 최종 결과의 판정처럼 표현하지 않는다.

`fork_turns=none`은 새 문맥을 만들 뿐 모델 계열까지 독립적으로 만들지는 않는다. 주 세션도 Sol이면 이를
`같은 모델의 새 문맥 자문`으로 표현하고, 다른 모델의 독립 검증처럼 과장하지 않는다.

최종 응답에 Sol 자문을 사용했다는 사실, 판정(병기 모드는 없음), 반영한 핵심, 반영하지 않은 핵심과 이유,
남은 위험을 짧게 밝힌다.
